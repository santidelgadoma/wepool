# WEPOOL — contexto para Claude Code

WEPOOL es un MVP de carpool institucional (piloto: ITAM) construido con Next.js 15 (App Router), TypeScript, Tailwind y Supabase (Postgres + PostGIS + Auth, RLS en cada tabla). Meta actual: llegar a una demo funcional para inversionistas.

**Antes de hacer cualquier cambio, lee estos dos archivos completos:**

- `PROGRESS.md` — changelog/bitácora de decisiones, en orden cronológico. Tiene el historial completo de qué se ha construido, qué bugs se encontraron y cómo se resolvieron, y qué sigue pendiente. Se actualiza con una entrada fechada nueva después de cada cambio importante — sigue ese mismo formato (fecha + título + bullets con el detalle técnico) al agregar la tuya.
- `docs/casos_de_uso.md` — catálogo completo de casos de uso (conductor + pasajero) construido leyendo el código real, no la documentación de producto. Es el backlog de pruebas de Playwright: cada caso tiene id (`CU-COND-*`, `CU-PAS-*`, `CU-COM-*`), pasos con los `id` reales de cada botón, y una columna de estado de automatización (✅/🟨/⬜). La sección F tiene el orden sugerido de los próximos specs — síguelo salvo que el usuario pida otra cosa.

Otros docs de referencia (menos prioritarios, y con partes desactualizadas ya señaladas en `docs/casos_de_uso.md` sección E): `docs/producto.md`, `docs/guion_demo.md` (el guion describe un flujo de confirmación viejo que ya no existe — ver hallazgo 1), `docs/arquitectura_mvp.md`, `docs/esquema_base_datos.md`.

## Pruebas e2e (Playwright) — convenciones establecidas

- **Usuarios de prueba dedicados por spec.** Nunca reusar `CONDUCTOR`/`PASAJERO` (u otros ya usados por specs existentes) en un archivo nuevo — cada spec define sus propios usuarios en `e2e/test-users.ts` y los registra en el arreglo `personas` de `e2e/global-setup.ts`. Esto evita que el estado de un spec contamine a otro sin importar el orden en que corran. Si dos usuarios conductores aparecen en el mismo spec, sus `fullName` deben empezar con una palabra distinta cada uno (el feed muestra `fullName.split(/\s+/)[0]` en la tarjeta — nombres con el mismo prefijo son indistinguibles por texto).
- **Localizar SIEMPRE por `id`, nunca por texto visible ni rol.** Prácticamente todo botón/link accionable del producto ya tiene un `id` determinístico (ver la tabla de "pasos" en `docs/casos_de_uso.md` para el id exacto de cada uno). Cuando un id incluye un UUID, usar el selector de atributo (`button[id^="unirme-"]`), nunca `#<uuid>` crudo (un id que empieza con dígito es CSS inválido sin escapar).
- **`workers: 1` en `playwright.config.ts` es intencional, no lo quites.** `next dev` compila cada ruta la primera vez que se pide y ese trabajo es esencialmente serial dentro de un proceso de Node — correr specs en paralelo contra un solo `npm run dev` genera falsos negativos (timeouts de navegación que no son bugs de la app, ver la entrada de `PROGRESS.md` del 2026-08-19 "dos bugs encontrados" para el diagnóstico completo con trace files).
- **Para debuggear un spec que falla:** `npm run test:e2e:headed` (navegador visible) o `npm run test:e2e:ui` (línea de tiempo de red/consola por paso, generalmente más útil). Los `trace.zip` que genera Playwright en fallos se pueden abrir con `unzip` + inspección manual de los `.jsonl` si hace falta ver network/console con detalle.
- **Requiere `SUPABASE_SERVICE_ROLE_KEY` y `NEXT_PUBLIC_SUPABASE_URL` en `.env.local`**, y las migraciones de `supabase/migrations/` aplicadas en el proyecto real de Supabase (hasta `0010` al momento de escribir esto — confirmar contra el directorio real si ha pasado tiempo; `0010_chat.sql` en particular todavía no se ha aplicado, ver nota de arriba). Si ves errores de Postgres tipo `invalid input value for enum trip_offer_status`, es casi seguro una migración sin aplicar, no un bug de la app.

## Flujo de trabajo esperado

1. Lee `PROGRESS.md` (al menos las últimas entradas) y `docs/casos_de_uso.md` sección F para saber en qué punto quedó el desarrollo y cuál es el siguiente caso de uso a automatizar.
2. Implementa el spec siguiendo las convenciones de arriba.
3. Córrelo de verdad (`npm run test:e2e` o `:headed`/`:ui` si falla) y confirma que pasa antes de darlo por hecho.
4. Marca el caso de uso correspondiente como ✅ en `docs/casos_de_uso.md` y agrega una entrada fechada en `PROGRESS.md` describiendo qué se hizo.
5. Commits normales de git (`git add` de los archivos tocados + `git commit`) — confirma con el usuario antes de hacer `git push` si no te lo pidió explícitamente.
